# 부하 테스트 (Phase 7)

## 목적

요청서 §56(Bot Load Test): 봇 10 / 20 / 32 / 50명으로 단계적으로 서버를 돌려 CPU, 메모리, Tick 시간(p95·p99), 패킷/s, 대역폭, GC를 기록하고 성능이 무너지는 지점이 있는지 본다. 64·100명은 이번에 측정하지 못했다(아래 "64·100명").

## 측정 환경

| 항목 | 값 |
|---|---|
| CPU | Intel(R) Core(TM) i9-14900K, 물리 코어 24, 논리 프로세서 32 |
| OS | Windows 11 Pro 10.0.26200 |
| .NET | SDK 10.0.401, Release 빌드 |
| 배치 | 서버와 봇이 같은 PC. 프로세스는 따로이고 접속은 127.0.0.1 UDP다 |
| 서버 설정 | `MaxPlayers=50`, 나머지 기본값(SimHz 30, Snapshot 15 Hz, Stats 10초) |
| 측정 날짜 | 2026-10-01 |

같은 PC라서 봇 프로세스가 서버와 같은 CPU를 나눠 쓴다. 다른 PC에서는 숫자가 다르다.

## 절차

단계마다 서버를 새로 띄운다(판 번호와 Loot 상태가 같은 조건에서 시작하도록). 포트는 7790이다.

```bash
dotnet build Server/ProjectH.Server.slnx -c Release

# 1. 서버 (N = 10, 20, 32, 50)
dotnet Server/src/ProjectH.Server/bin/Release/net10.0/ProjectH.Server.dll --Server:Port=7790 --Server:MaxPlayers=50 --Server:DevRespawn=true > load-server-N.log 2>&1 &

# 2. 4초 뒤 봇을 2분 돌린다
dotnet Server/src/ProjectH.Bots/bin/Release/net10.0/ProjectH.Bots.dll --port 7790 --count N --duration 120 --connect-interval-ms 50 > load-bots-N.log 2>&1

# 3. 서버를 끈다(자기가 띄운 프로세스만 pid로. 이름으로 끄지 않는다)
```

- **`DevRespawn=true`로 잰다.** 배틀로얄 모드에서는 죽은 봇이 입력을 멈춰서(계획 단계의 50명 실측에서 1분 만에 살아 있는 봇이 20명으로 줄었다) "50명" 행이 실제로는 더 적은 인원의 부하가 된다. `DevRespawn`에서는 3초 뒤 부활하므로 N명이 2분 내내 움직이고 싸운다.
- 추가로 배틀로얄 모드 50명 1회를 `DevRespawn` 없이 같은 명령으로 쟀다(표의 "BR").
- 봇 프로세스 CPU: 봇을 `Start-Process -PassThru`로 띄워 pid를 얻고, 실행 중 0.2초마다 `(Get-Process -Id pid).TotalProcessorTime`을 읽어 시작 값과 종료 직전 값의 차를 실행 시간(약 120초)으로 나눴다. 1.0 = 코어 하나 100%다.
- 서버 `cpu%`는 Stats 로그의 값이다: 프로세스 CPU 시간 증가 / (경과 시간 × 논리 프로세서 32) × 100. 코어 하나를 다 쓰면 약 3.1%다.
- 집계: 서버 Stats 줄 12개 중 처음 2개(약 20초: 접속 램프와 JIT)를 버리고 10개를 썼다. 봇 로그도 처음 2줄을 버리고 나머지 9줄(10초 줄 9개)의 `alive`를 썼다. Tick 백분위는 10개 줄의 최댓값, 패킷·바이트·`cpu%`는 평균이다. Tick은 로그에 소수 둘째 자리(0.01 ms)까지만 나온다.

- `inputDrops`·`badPackets`는 10개 줄의 합, `lateTicksSkipped`·`exceptions`는 마지막 줄의 누적값이다.
- `DevRespawn`에서도 `alive`가 N보다 작다. 죽은 뒤 3초 부활 대기 중인 봇이 항상 있기 때문이다. 서버 `players`는 모든 단계에서 N이었다(접속은 모두 유지됐다).
- BR 행: 경기가 시작되자 `alive`가 36 → 25 → 21 → 18명으로 줄었고, 이후 측정 구간 끝까지 18명에서 변하지 않았다(경기 상태는 계속 `Playing#1`). 죽은 봇은 입력을 멈추므로 서버 pktIn/s가 `DevRespawn` 50명의 절반 이하(621)다. 반면 bytesOut/s는 `DevRespawn` 50명과 거의 같다(881 KB/s). `alive`가 18명에서 멈춘 것은 봇 문제가 아니라 자기장 타이밍 때문이다. 기본 `zones.json`에서는 120초 측정이 끝날 때까지 원이 아직 70 m 폭이고, 봇은 빈손으로 시작한다.

## 관찰

- **무너지는 지점은 없었다.** 모든 단계에서 `lateTicksSkipped=0`, `exceptions=0`, `inputDrops=0`, `badPackets=0`, 접속 끊김 없음이었다. Tick 예산(SimHz 30 = 33.3 ms)에 비해 가장 큰 단일 Tick(`max`)도 50명에서 1.81 ms였다.
- **가장 크게 늘어난 값은 `bytesOut/s`다.** 10명 39 KB/s에서 50명 901 KB/s로 약 23배다. 인원이 5배일 때 Snapshot 크기(플레이어 수에 비례) × 수신자 수(인원에 비례)가 곱해지므로 인원의 제곱에 가깝게 자란다. pktOut/s는 같은 구간에서 약 7.8배(246 → 1916)다.
- Tick 시간도 50명에서 늘었다(p50 0.05 → 0.14 ms, p99 0.22 → 0.94 ms, 32명 대비). 그래도 p99 기준으로 예산(33.3 ms)의 3% 이하다(가장 큰 단일 Tick `max`는 50명에서 1.81 ms로 최대 5.4%). 서버 CPU는 논리 32코어 중 0.13%(코어 0.04개 정도)이고, GC는 한 번도 일어나지 않았다.
- 봇 프로세스(50명 3.87% = 코어 0.04개 정도)는 서버와 비슷한 양을 쓴다. 이 PC에서는 어느 쪽도 한계에 가깝지 않다.
- 한계: 루프백(127.0.0.1)이라 실제 네트워크의 지연·손실·대역폭 제한이 없다. 50명 901 KB/s(약 7.2 Mbps)는 실제 서버 회선에서는 의미 있는 값이다.
- 측정 기록: 첫 시도에서 봇 CPU가 0으로 나와(`TotalProcessorTime`을 종료 후에 읽는 방식) 10명 단계를 버리고 실행 중 샘플링으로 고쳐 다시 쟀다. 표의 값은 모두 고친 뒤 잰 값이다.

## 64·100명

요청서 §56은 64·100명도 요구하지만 이번에는 측정하지 못했다(D11).

- 한 경기 인원 상한이 50명이다(`MaxSnapshotEntities`). Snapshot 한 개(50명일 때 1167 B)가 분할 없이 한 데이터그램으로 전송되는 한계다.
- 위 관찰대로 `bytesOut/s`는 인원의 제곱에 가깝게 자라므로, 50명을 넘기면 Snapshot 크기와 송신량이 같이 문제가 된다.
- Phase 8(Optimization)에서 Interest Management(수신자마다 근처 플레이어만 전송) 또는 Snapshot 분할을 넣은 뒤 64·100명을 같은 절차로 측정한다.
