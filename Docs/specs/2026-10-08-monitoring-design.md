# Monitoring Server — 설계 Spec

## Context

요청서는 `Docs/requests/2026-10-08-monitoring-request.md`(§1–§92)다. 목표는 **별도 프로세스의 Monitoring Server**와 Game Server의 **Collector·Sender**, 그리고 **정적 Web Dashboard** 하나: Online/Offline, 접속자, Match, Tick P50/P95/P99/Max, CPU, Memory, Network, Error. 가장 중요한 규칙은 Monitoring 장애가 Game Server로 전파되지 않는 것(§7)과 Game Loop에서 HTTP를 기다리지 않는 것(§8)이다.

**지금 구조에서 확인한 사실(`phase19-vehicle` 69a3f63 기준):**

- **Tick 통계는 `TickMetrics`(Game Loop 전용 링 1024, nearest-rank 백분위)가 계산한다.** `LogStats`가 `StatsIntervalSeconds`(기본 10 s)마다 `Compute()` 뒤 `Reset()`하므로 그 인스턴스는 다른 창(window)을 답할 수 없다. QA는 같은 이유로 자기 링(`QaObservation`)을 따로 둔다.
- **CPU·메모리·GC는 `LogStats`가 이미 계산한다.** CPU = 프로세스 전체 처리 시간 증가분 ÷ (경과 초 × 코어 수) × 100(모든 코어 = 100 %). QA는 할당 없는 `Environment.CpuUsage.TotalTime`을 쓴다. 메모리는 `Environment.WorkingSet`, GC는 `GC.CollectionCount(n)`.
- **Network는 `ServerStats`(LiteNetLib 스레드가 Interlocked로 더함)에 누적값(`PacketsInTotal` 등, Game Loop 스레드에서만 읽음)이 있다.** `TakeDelta()`는 Stats 로그가 소비하므로 Monitoring이 부르면 로그 값이 깨진다.
- **오류·접속 수치는 `HealthCounters`에 있다.** `TickFailures`, `LoopFailures`, `PlayerFailures`, `CallbackErrors`, `BadPacketsTotal`, `DisconnectTimeouts/Others`, 게이지 `Peers/Players/Graced/MatchState`. `ServerMeter`가 이것을 .NET Meter로도 내보낸다(dotnet-counters).
- **Match는 하나다.** `GameLoop`가 `Match` 하나를 소유하고 `Flow.State`·`Flow.Round`·`PlayerCount`·`GracedCount`를 가진다. "ActiveMatches" 개념은 없다.
- **중요한 bounded queue는 `MatchHistoryQueue`(DB 쓰기, 용량 `Persistence:QueueCapacity` 16, `Count` 어느 스레드나 읽음)다.**
- **Background Worker 선례:** `MatchHistoryWriter`·`StatsQueryService`·`QaHttpService`는 `IHostedService`/`BackgroundService`이고 `ServerHost.CreateBuilder`에서 등록 순서로 종료 순서를 정한다. 설정은 섹션별 Options 클래스 + `Validate()`(시작 때 실패). 환경변수는 `섹션__키`.
- **Game Server는 이미 `Microsoft.AspNetCore.App` FrameworkReference를 가진다**(QA HTTP). 테스트에서 loopback Kestrel을 띄울 수 있다.
- **QA 도구와 서버는 프로젝트를 공유하지 않는다**(JSON 레코드를 양쪽에 둠). `ProjectH.Shared`는 Client/Server 프로토콜 전용이다(`game-core-rules` 4절). `ProtocolConstants.ProtocolVersion = 18`.
- **서버 Stress 측정 도구:** `QA/Scenarios/Stress/baseline.json`(10/25/50/75/100명), `ServerProcessManager`가 `--Server:키=값` 식 override로 서버를 띄운다.

## 검증 계획

1. `dotnet build Server/ProjectH.Server.slnx`, 서버·Monitoring·QA 테스트 두 번(flake 확인).
2. D16의 실제 프로세스 검증(§67·§91)과 Stress 측정(§90) — 실측값만 보고.
3. QA `smoke`·`pre-push`(Game Server 회귀 없음).
4. 리뷰: safety(항상) + server-concurrency(슬롯·Store Lock) + queue-cache(링·슬롯·HttpClient Lifetime) + server-hotpath(Tick 경로의 RecordTick·null 검사). deadlock은 Lock이 하나뿐이라 D9에서 검토 완료, 리뷰어가 확인만.
5. 최종 보고는 요청서 §92 형식.
