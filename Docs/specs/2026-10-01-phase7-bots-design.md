# Phase 7 Bots — 설계 Spec

## Context

Phase 6까지 만든 것은 다음과 같다.

- 160 × 160 m 맵: 지형, POI, 건물, Loot 50곳, 투입 지점 24곳
- 서버가 판정하는 이동·전투·Loot·Zone·경기 흐름. 경기는 2명 이상이면 시작한다.
- 서버 통계 로그: 10초마다 Tick p50/p95/p99/max, 패킷·바이트/s, GC, 메모리

경기를 시험하려면 지금은 Unity Client를 여러 개 띄워야 한다. 서버 부하는 측정한 적이 없다.

원래 요청서의 Phase 7은 다음을 구현한다.

```text
Bot Movement / Loot / Combat / Zone Movement / Load Test Bot
```

관련 조항은 다음과 같다.

- §35 Bot: 멀티플레이어 테스트용이다. 실제 Client를 실행하지 않아도 서버 부하를 만들 수 있게 한다.
  - 기본 행동: 이동, Loot 탐색, 적 탐색, 조준, 발사, Zone 이동
  - AI 품질은 우선순위가 아니다. 목적은 Match 테스트와 Server 부하 테스트다.
- §56 Bot Load Test: 10, 20, 32, 64, 100명으로 단계적으로 테스트한다.
  - 기록 항목: CPU, Memory, Tick Time, P95, P99, Packet/sec, Bandwidth, GC
  - 성능이 무너지는 지점을 확인한다.
- §7 초기 규모: 2–4명 → 8–16명 → 32명 → 64명 → 100명. 단계마다 측정 후 확장한다.

**성공 기준:**

- Unity 없이 명령 하나로 봇 N명(1–50)을 서버에 접속시킨다.
- 봇은 다음을 한다.
  - Loot를 줍는다.
  - 적을 찾아 쏜다.
  - 회복한다.
  - Zone 안으로 이동한다.
- 봇끼리, 또는 봇과 사람이 섞여 경기가 시작부터 승자 결정까지 끝나고, 다음 판이 이어진다.
- 서버는 봇을 따로 구분하지 않는다. 봇도 일반 Client와 같은 패킷과 같은 검증을 거친다.
- 부하 테스트 절차를 문서로 남긴다. 10 / 20 / 32 / 50명 측정값을 기록한다.
- 봇의 판단 규칙과 실제 서버 위 동작은 `dotnet test`로 검증한다.

AI 품질은 이 단계의 목표가 아니다(§35). |
| D5 | **이동은 직선 조향과 막힘 탈출이다.** 목표 방향으로 걷고, 10 m 넘게 남았으면 달린다. 막힘 탈출 규칙은 다음과 같다.<ul><li>움직이려는데 0.5초 동안 0.3 m도 못 갔으면 한 번 점프한다.</li><li>1초째도 막혀 있으면 좌우 90° 중 하나로 1–2초 우회한다.</li><li>8초 동안 목표에 가까워지지 않으면 그 목표(아이템, 지점)를 30초 동안 버린다.</li></ul> | 맵이 열린 들판과 문 있는 단층 건물이라 직선 + 우회로 대부분 도달한다. 길찾기(NavMesh, A*)는 맵 데이터 추가와 큰 코드가 필요하고, 이 단계의 목표(경기·부하 테스트)에는 과하다. 목표를 버리는 규칙이 있어 영원히 끼어 있지 않다. | 건물 안 Loot를 놓칠 때가 있다. 길찾기는 필요해질 때 추가한다. |
| D6 | **조준.**<ul><li>눈(내 발 + 1.6 m)에서 적의 가슴(적 발 + 1.2 m)을 향한다. 적 위치는 마지막으로 받은 Snapshot의 값이다.</li><li>오차: Yaw·Pitch에 ±(1° + 0.04° × 거리 m)의 균등 오차를 0.3초마다 다시 뽑는다.</li><li>ViewTick: 마지막 Snapshot의 서버 Tick이다.</li></ul> | 오차가 없으면 봇이 거의 모든 탄을 맞혀 교전이 비현실적으로 짧다. 0.3초마다 바꾸면 연사가 한 덩어리로 흩어진다. ViewTick을 실제로 본 Tick으로 보내야 서버 Lag Compensation이 사람과 같은 방식으로 판정한다. | 수치는 옵션이 아닌 상수다. 조정은 코드 한 곳에서 한다. |
| D7 | **시선 검사는 봇 쪽 계산이다.** 눈에서 가슴까지 0.5 m 간격으로 점을 찍는다. 점이 박스 안이거나 지형 아래면 막힌 것이다. 서버 `HitScan`은 쓰지 않는다. | 봇은 Client다. 서버 코드를 참조하면 경계가 무너진다. 0.5 m 표본은 벽(0.25 m 이상)을 놓칠 수 있지만, 놓쳐도 서버가 벽에 맞게 판정하므로 결과가 틀리지 않는다. 같은 적에게 45 Tick(자동 무기 약 1.5초) 동안 쏴서 한 번도 안 맞으면 그 적을 5초 동안 무시한다. | 얇은 벽 너머로 몇 발 낭비한다. |
| D8 | **입력 전송은 Unity Client와 같다.** Tick마다 Seq를 1 올리고, 패킷에 최근 입력 3개를 담는다(유실 대비). 눌림 버튼(점프, E, R, 회복)은 그 Tick에만 싣는다. | 서버가 기대하는 입력 흐름(peer별 입력 상한 `SimHz × 2`/s, Seq 중복 제거)을 그대로 지킨다. 봇 때문에 생기는 잘못된 패킷 집계(`badPackets`)가 없어야 부하 결과를 믿을 수 있다. | 없음. |

| D10 | **서버 통계에 CPU 사용률을 더한다.** 10초 Stats 로그에 `cpu%`(프로세스 CPU 시간 증가 / (경과 시간 × 코어 수))를 넣는다. 다른 서버 코드는 바꾸지 않는다. | §56의 기록 항목 중 서버 로그에 없는 것은 CPU뿐이다. 나머지(Tick p50/p95/p99, 패킷·바이트/s, GC, 메모리)는 이미 있다. | 없음. |
| D11 | **부하 테스트는 10 / 20 / 32 / 50명까지 측정한다.** 64·100명은 이번에 측정할 수 없다.<ul><li>이유: 한 경기 인원 상한이 50명이다(`MaxSnapshotEntities`). Snapshot 한 개(1167 B)가 분할 없이 전송되는 한계다.</li><li>50명을 넘기려면 Interest Management나 Snapshot 분할이 필요하다. 이것은 Optimization 단계(Phase 8)의 일이다.</li></ul>절차와 결과는 `Docs/LoadTest.md`에 남긴다. 측정 환경은 Release 빌드이고, 서버와 봇을 같은 PC에서 각각 2분씩 돌린다. | §56은 성능이 무너지는 지점을 찾으라고 한다. 지금 구조의 상한은 50명이고, 그 안에서 측정값을 남겨야 Phase 8에서 무엇을 최적화할지 정할 수 있다. 같은 PC에서 돌리면 봇 CPU가 서버와 섞이므로, 봇 프로세스 CPU도 함께 적는다. | 다른 PC에서는 숫자가 다르다. 문서에 측정 환경(CPU, 코어 수)을 적는다. |
| D12 | **지금 넣지 않는 것:** 길찾기(NavMesh, A*), 봇 난이도 단계, 팀 AI, 서버 안 봇, 50명 초과, 재접속, Unity에서 봇 전용 표시. | 경기·부하 테스트에 필요 없거나(§35 "AI 품질은 우선순위가 아니다") 뒤 단계(Phase 8, 10) 범위다. 봇은 Unity Client에서 일반 원격 플레이어로 보인다. | 없음. |

## 1. 구조 (`Server/src/ProjectH.Bots`)

| 파일 | 책임 |
|---|---|
| `BotOptions` | 명령줄 파싱과 검증(D9) |
| `BotConnection` | 봇 하나의 LiteNetLib 수동 모드 연결. 패킷을 읽어 `BotView`를 갱신하고 입력 패킷을 보낸다. |
| `BotView` | 봇이 아는 세계(D3): 내 상태, 다른 플레이어(최대 50), 월드 아이템(최대 256), 경기·Zone 상태, 무기·아이템 Catalog |
| `BotBrain` | 판단(D4)과 그 결과의 입력 하나(`InputCommand`)를 만든다. 순수 계산이고, 시각과 난수는 인자로 받는다. |
| `BotSteering` | 직선 조향, 막힘 탈출(D5) |
| `BotAim`, `LineOfSight` | 조준 각과 오차(D6), 시선 검사(D7) |

- 모든 컬렉션은 상한이 있다(플레이어 50, 아이템 256).
- Tick 경로(판단·입력)는 할당하지 않는다. 테스트로 고정한다.

## 3. 테스트

**단위 (xUnit, `ProjectH.Server.Tests`가 `ProjectH.Bots`를 참조):**

- **`BotBrain` 규칙별:**
  - 죽었으면 입력 없음
  - 경기 전이면 정지
  - Zone 밖이면 다음 원 쪽으로
  - 보이는 적이면 조준·발사
  - 탄이 없으면 장전 또는 무기 교체
  - 회복 조건
  - 쓸모 있는 아이템이면 그쪽으로 가서 E
  - 배회 지점은 Zone 안
- **`LineOfSight`:** 벽 뒤는 안 보인다. 언덕 너머는 안 보인다. 트인 곳은 보인다.
- **`BotAim`:** 오차 0이면 각이 서버 `CombatRules`의 각 정의와 맞는다. 오차는 범위 안이다.
- **`BotSteering`:** 막히면 점프 → 우회 → 목표 포기
- **`BotOptions`:** 범위 검증
- **할당:** 판단 Tick이 할당하지 않는다.

**통합 (서버 `GameLoop`를 같은 프로세스에서 돌리고 봇이 실제 UDP로 접속):**

1. `DevRespawn` 서버, 빈손, 무기만 나오는 Loot → 봇 1명이 20초 안에 무기를 줍는다.
2. `DevRespawn` 서버, 전투 장비 → 봇 2명이 30초 안에 한 명을 처치한다.
3. 경기 서버(짧은 카운트다운, 짧은 Zone) → 봇 4명이 경기를 끝까지 하고, 참가한 봇이 `MatchResult`를 받으며, 다음 판 카운트다운이 시작된다.

**부하 테스트(수동, 문서에 기록):** 10 / 20 / 32 / 50명, 각 2분, Release.

## 4. 범위 밖

D12의 항목.
