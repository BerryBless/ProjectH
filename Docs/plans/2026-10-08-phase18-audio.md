# Phase 18 Gameplay Audio — 구현 기록 (Spec과 다른 점)

설계: `Docs/specs/2026-10-08-phase18-audio-design.md`(D1–D13). 동작 설명: `Docs/Audio.md`, 패킷: `Docs/Networking.md`. 이 문서에는 구현하면서 Spec에 없던 것을 정했거나 Spec과 다르게 한 것만 적는다.

## 서버

| # | 내용 | 이유 |
|---|---|---|
| S1 | `WorldSound`는 휘두르기 하나에 하나다. 대상이 부서지면 `HarvestDestroyed`만 보낸다(HarvestHit와 둘 다 보내지 않음). 위치는 휘두르기가 맞은 점이다. 건설 조각을 친 휘두르기는 보내지 않는다(BuildEvents Health/Destroyed가 있다). | 한 사건 = 한 소리. |
| S2 | `WorldSound` 거리(30 m)는 받는 사람 몸 위치로 잰다. 죽은 사람·관전자도 몸 위치를 쓰고, 연결이 끊긴 유예 플레이어는 뺀다. | 서버는 관전 카메라 위치를 모른다. |
| S3 | `DamageTaken.FlagsFor`는 "전 실드 > 0이고 실제로 줄었을 때"만 실드 맞음으로 본다. 낙하 피해는 실드를 건드리지 않아 Flags 0이다. | 피해가 적용되지 않은 경우(이미 죽은 대상)를 거른다. |
| S4 | 2인자 `BuildEvents.TryReadDestroyed`(이유를 버림)를 남겼다. 5 B 전체를 읽는다. | 봇·테스트 같은 기존 호출자가 그대로 컴파일된다. |

## Client

| # | 내용 | 이유 |
|---|---|---|
| C1 | 무기 → 총성은 무기 id가 아니라 카탈로그 성질(로켓, 산탄, Heavy·Medium·Light 탄, 자동·반자동)로 고른다. 모르는 id는 AR 소리. | 무기 표가 바뀌어도 맞다. |
| C2 | Spec이 정하지 않은 들리는 거리: 문 20 m, 수류탄 던지기 40 m, 미끄럼 25 m, 기절 끌림 12 m, 재투입 15 m. | 소리 성격(작은 동작)에 맞췄다. |
| C3 | 원격 Ground 모드의 "수직 이동이 크면 발소리를 쉰다"는 발밑 표면과의 높이 차 0.35 m로 판단한다. | 언덕을 달릴 때 발소리가 끊기지 않게 한다. |
| C4 | 붕괴 소리는 Spec D6의 "칸마다 하나" 대신 프레임마다 가장 가까운 하나다. | 큰 붕괴가 여러 패킷으로 나뉘어 와도 소리가 몰리지 않는다. |
| C5 | 이벤트 처리기의 현재 Tick은 `max(EstimatedServerTick, ServerClock.LatestTick)`이다. | 입장 직후에는 보간 Tick이 0이다. |
| C6 | 투사체 재전송 판정은 Spec의 "StartTick이 0.2 s보다 오래됨" 대신 "StartTick ≤ 입장·Resume 응답의 ServerTick"이다. | 리뷰에서 발견: 서버는 재전송의 StartTick을 지금 Tick으로 보내므로 0.2 s 규칙이 걸리지 않아, 날고 있던 모든 투사체가 입장 때 발사음을 냈다. 실제 발사는 시뮬레이션 중인 Tick(응답 Tick + 1 이상)을 싣는다. |
| C7 | 믹서 큐가 가득 차면 큐에서 가장 덜 중요한 요청보다 새 요청이 나을 때만 바꿔 넣는다. 지난 Mix의 듣는 위치에서 거리 밖인 3D 요청은 큐에 넣지 않는다(droppedDistance). | 리뷰: 큰 BuildEvents 패킷의 먼 피해 소리가 큐를 채워 발소리·붕괴·총성이 버려질 수 있었다. |
| C8 | 중복 판정 표(64쌍)가 가득 차면 중복 간격이 이미 끝난 칸을 먼저 덮고, 없으면 간격이 가장 먼저 끝나는 칸을 덮는다. | 리뷰: 차례로 덮어 아직 유효한 칸이 덮여 중복 소리가 났다. "가장 오래된 시각" 규칙은 방금 들어온 쌍을 먼저 밀어내 테스트에서 틀렸다. |
| C9 | 문 소리의 만료형 기준 상태(1 s)는 경기 시작에만 건다(Transport 부활, Starting → Playing·FinalPhase). 라운드 리셋·개발 모드 부활에는 걸지 않는다. | 리뷰: 서버는 경기 시작(`CloseAll`)에만 문을 바꾸므로, 라운드 리셋 뒤의 기준 창이 실제 문 변화를 삼켰다. 자기장 단계가 하나인 경기는 시작 Tick에 FinalPhase가 된다. |
| C10 | 내 예측 문은 1 s(`PredictedDoors.PredictionSeconds`) 안에 예측과 반대로 바뀐 서버 상태를 듣지 않는다. 서버가 끝내 확인하지 않은 예측은 1 s 뒤 되돌아가는 소리를 한 번 낸다. `PredictedDoors`(충돌 예측)는 바꾸지 않았다. | 리뷰: 다른 문의 DoorStates가 먼저 오면 모든 예측이 지워져 키 한 번에 열림·닫힘·열림이 났다. |
| C11 | 자기장 밖 피해 소리는 서버 패킷 없이 Client 1 s 타이머로 낸다(밖에 나간 뒤 1 s부터). | 서버가 자기장 피해에 DamageTaken을 보내지 않는다. |
| C12 | `droppedBudget`은 들어가지 못한 요청과 교체로 끊긴 목소리를 함께 센다. | QA 카운터 하나로 예산 압박을 본다. |
| C13 | 편집 Ok에 설치 소리를 내던 Phase 13.5 `OnBuildResult` 버그를 함께 고쳤다. | 소리 출처 표대로 편집은 편집 소리. |

## QA

- `/qa/status`에 처음으로 중첩 객체 `audio`가 생겼다: `audio.plays.<SoundKind>`, `audio.active`, `audio.droppedBudget`, `audio.droppedDuplicate`, `audio.droppedDistance`, `audio.queueOverflow`. 시나리오는 `waitForUnity` 조건 `audio.plays.GunAR`, `save` 경로 `actor.unity.audio.plays.GunAR`로 읽는다.
- Unity 시나리오: `QA/Scenarios/Audio/` 5개(audio_gunshot, audio_footstep, audio_build, audio_budget, audio_no_duplicate)를 `suite:unity`에 넣었다. 소리 품질·방향감은 `QA/Scenarios/Manual/audio_listen.json`으로 사람이 듣는다.

## 측정

`stress-quick` 5/5 PASS(50명). Mixed Match Tick p95 0.314 ms, 이전 기준선 대비 50 % 넘게 나빠진 지표 없음. 서버 변경은 패킷 바이트 몇 개와 채집 휘두르기당 거리 비교뿐이라 Tick 비용 변화가 없다.

## Known Issues

- 소리 품질·방향감은 자동 검증하지 않는다(로직 카운터만). 수동 확인 목록은 `audio_listen.json`.
- 서버가 확인하지 않은 내 문 예측은 1 s 뒤 되돌아가는 소리가 난다(실제로 문이 원래대로 돌아가는 것이 보이는 시점과 같다).
- 큰 폭발로 한 프레임에 큐(64)보다 많은 가까운 요청이 오면 덜 중요한 것부터 버려진다(`queueOverflow`로 센다).
- Unity Editor에서의 실제 소리는 batchmode에서 들을 수 없어 수동 확인 전까지 미확인이다.
