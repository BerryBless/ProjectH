# Phase 13.5 Building Edit — 구현 기록 (Spec과 다른 점)

설계: `Docs/specs/2026-10-07-phase13_5-building-edit-design.md`(D1–D14). 동작 설명: `Docs/Building.md` "편집". 이 문서에는 구현하면서 Spec에 없던 것을 정했거나 Spec과 다르게 한 것만 적는다.

## 서버

| # | 내용 | 이유 |
|---|---|---|
| S1 | 상태가 지금과 같은 편집은 D5 4단계(유효성) 바로 뒤에서 `Ok`로 답한다. 사거리·시선·충돌과 0.1초 간격을 보지 않는다. 상태를 실제로 바꾼 편집만 간격을 쓴다. | 재전송과 반복 확정이 위치와 관계없이 멱등이 되고, 바뀐 것이 없는 요청은 서버 큐를 채우지 않는다. |
| S2 | 소유자 0인 조각(QA `spawnBuildPiece`가 놓은 조각)은 아무도 편집할 수 없다(`NotOwner`). | 주인이 없는 조각에 편집 권한을 주지 않는다. QA 시나리오는 Actor의 `build`로 조각을 놓는다. |
| S3 | 편집은 진행 중인 회복을 끊지 않는다. 배치는 지금처럼 끊는다. | Spec에 언급이 없다. 편집은 자원을 쓰지 않는 빠른 동작이다. |
| S4 | 충돌 검사 범위. 벽·바닥은 다시 채워지는 칸만 본다. 지붕은 새 모양 전체를 본다. 경사면(경사로 회전, 한쪽 경사 지붕)은 배치처럼 Vault 경로와 올린 몸을 본다. 올린 몸 검사는 새 모양을 Grid에 잠깐 넣고 확인한 뒤 되돌린다. | 옛 경사면 때문에 잘못 거부하지 않는다. 모두 Game Loop 스레드에서 처리하고 그 사이에 다른 읽기가 없다. |
| S5 | 경사로 회전에서는 잃은 이웃뿐 아니라 그 경사로 자신도 붕괴 탐색 시작점에 넣는다. | 새 이웃이 옛 연결로만 받쳐지던 경우를 놓치지 않는다. 탐색은 Tick 끝에 한 번만 돈다. |
| S6 | QA Control 명령 `editBuild`(`Match.EditPieceById`, 소유자·사거리 검사 없음)를 더했다. 실제 반영은 `TryEdit`와 같은 `ApplyEdit`다. | 유예 중에는 소유자가 요청을 보낼 수 없어 재접속 시나리오에 서버 쪽 편집이 필요하다. Match에 QA 분기는 없다. |
| S7 | `Edited` 리더는 id 0과 14–15비트만 거부한다. 종류별 유효성은 받는 쪽이 `BuildEdit.TryApply`로 본다. | 기록에 조각 종류가 없다. |
| S8 | QA 시나리오 `building_edit_damage`와 `building_edit_destroy_race`는 "곧바로 이어서"를 본다. 정확히 같은 Tick은 서버 테스트(`BuildEditTests`)가 본다. | QA 단계는 서버 Tick을 고를 수 없다. |

## Client

| # | 내용 | 이유 |
|---|---|---|
| C1 | 확정 조각의 편집 예측은 예측 충돌 Grid에 넣는다. 예측 배치 조각은 지금처럼 넣지 않는다. game-core-rules §4("확정 조각만")의 예외다. 하네스 규칙 갱신은 사용자 확인이 필요하다. | Spec D11. 문을 열고 바로 지나갈 때 예측 보정이 생기지 않는다. |
| C2 | 조각에 맞지 않는 Edited 기록은 그 기록만 무시하고 `Ignored`로 센다. 패킷의 나머지는 계속 처리한다. | Client에는 잘못된 패킷 카운터가 없다. |
| C3 | 순번 카운터와 초당 20개 상한을 배치와 편집이 같이 쓴다(`BuildRequestCounter`). | 서버 상한이 둘의 합계라, 나눠 세면 서버가 잘못된 패킷(`BuildRate`)으로 센다. |
| C4 | Ok를 받았을 때 확정 모양이 이미 예측과 같으면 예측을 바로 지운다. 다르면 Edited·Placed·Sync가 오거나 1초가 지난 뒤 지운다. 연달아 편집하면 마지막 예측 하나만 남는다. | 멱등 Ok, 또는 Edited가 결과보다 먼저 온 경우. |
| C5 | 확정할 상태가 지금 상태와 같으면 요청을 보내지 않고 편집 모드만 끝낸다. 잘못된 선택에서 H를 누르면 편집 모드를 유지하고 안내를 보인다. | 불필요한 요청을 보내지 않는다. |
| C6 | 지붕 선택에서 대각 2칸은 통로(Edit 6)다. | Spec에 통로를 고르는 선택이 없었다(Spec D10에 반영). |
| C7 | 편집 Mesh 캐시 키는 (종류, 벽 회전, Edit)다. 상한은 1024 + 16 + 7이다. | 리뷰 Medium 지적. 회전이 빠지면 서쪽 벽이 남쪽 벽 Mesh로 그려진다. |

## QA 도구

- QA가 띄우는 서버의 기본값에 `Server:ConnectBurstPerIp=1000`을 넣었다(`ServerProcessManager.BuildArguments`). 서버 리뷰 수정 9302b10의 IP당 접속 제한(처음 20개까지 한꺼번에 허용, 이후 초당 5개)이 qa-tool 병합 뒤 stress 시나리오를 막았기 때문이다. 모든 Actor가 127.0.0.1에서 접속하므로 50명 접속에서 29번이 거절되었다. 제한기는 켠 채로 두고 시나리오가 값을 바꿀 수 있다. Phase 13.5와는 별개의 병합 회귀 수정이다.

## 측정 (server-engineer, Release, 모든 벽 자리를 채운 블록 안에서 Gather + Step 한 번)

| 상태 | µs / step |
|---|---|
| 편집 전 HEAD | 1.96 |
| Edit 0 | 2.20 |
| 모두 문 | 4.8 |
| 모두 창 | 5.6 |
| 최악(상자 5개) | 6.7 |

100명이 모두 최악의 블록에 있어도 33 ms Tick당 0.7 ms 미만이다. 추가 최적화는 하지 않았다.

## Known Issues

- Q나 무기 키를 누른 뒤 약 33 ms(한 Tick) 안에 H를 누르면 편집이 시작됐다가 다음 프레임에 바로 취소된다. 아직 서버로 가지 않은 도구 전환 입력을 보고 취소하기 때문이다.
- 서버 큐 8개를 배치와 편집이 같이 쓴다. 배치 대기와 편집 예측이 합쳐 8개를 넘으면 서버가 `RateLimited`로 거절하고, Client는 그 요청을 롤백한다.
