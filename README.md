# ProjectH

서버 권한(Server-authoritative) 멀티플레이 배틀로얄을 처음부터 만든 개인 프로젝트다. Unity 6 Client, .NET 10 Dedicated Server(LiteNetLib UDP), MySQL 8.4를 쓴다.

이 문서에는 **무엇을 했는지**와 **왜 그렇게 정했는지**만 적는다. 기능 상세·실행 방법·수치는 [Docs/](Docs/)에 있다.

## 전체를 관통한 판단

| 판단 | 이유 |
|---|---|
| **Client는 입력만 보낸다.** 위치·속도·명중 대상·아이템 Id는 보내지 않는다 | 서버가 같은 입력으로 결과를 만들면 속도 조작·순간이동·가짜 명중이 검증 없이도 구조적으로 불가능하다 |
| **Shared는 최소로 둔다.** 패킷, 그리고 예측이 서버와 같은 답을 내야 하는 이동·충돌·지형·건설 격자만 넣는다 | Client와 서버가 같은 코드를 써야 보정이 생기지 않는다. 규칙(피해, 검증, 지지)은 서버에만 둔다 |
| **Game Loop 스레드 하나가 경기 상태를 소유한다.** 스레드 사이는 크기가 정해진 Channel, 카운터는 `Interlocked`다 | Lock이 없으면 Deadlock도 Lock Ordering 문제도 없다 |
| **Game Loop는 아무것도 기다리지 않는다.** DB 저장·전적 조회·QA 명령은 큐로 넘긴다 | DB가 느리거나 꺼져도 Tick이 밀리지 않는다 |
| **모든 Collection에 상한과 넘칠 때의 규칙이 있다** | 100명 서버가 오래 돌아도 메모리가 늘지 않는다 |
| **최적화는 측정한 뒤에, 병목에만 한다** | 측정해 보니 서버 Tick은 예산(33 ms)의 1 % 아래였다. 그래서 CPU 최적화는 하지 않고 실제 한계였던 Snapshot만 고쳤다(Phase 8) |
| **Phase마다 "지금 넣지 않는 것"을 적는다** | 범위가 새지 않게 하고, 다음 Phase의 입력으로 쓴다 |

## Phase별 행동과 판단

### Phase 0 — 네트워크 이동 동기화
- **행동:** 서버 Tick 루프, 입력·Snapshot 프로토콜, 내 캐릭터 예측과 보정, 원격 보간을 만들었다.
- **판단:**
  - LiteNetLib 위에 수기 직렬화(`Span`, `TryRead`)를 얹었다. 잘못된 패킷이 예외가 아니라 실패 값이 되게 하기 위해서다.
  - 수신 스레드와 Game Loop 스레드를 나누고 Channel로 이었다.
  - Simulation은 30 Hz, Snapshot은 15 Hz다.

### Phase 1 — 캐릭터 프로토타입
- **행동:** 박스 충돌, 어깨 카메라, 로컬 발사 연출을 만들었다.
- **판단:**
  - 충돌은 AABB에 축 분리 Sweep(X→Z→Y)이다. 단순하고 서버·예측이 같은 결과를 낸다.
  - 지형 데이터를 Shared에 둔다(첫 Shared 예외 확장).
  - 카메라는 Client 전용이다.

### Phase 3 — 서버 권한 전투
- **행동:** Hitscan, 지연 보상, 사망·부활, HUD를 만들었다.
- **판단:**
  - 발사는 별도 패킷이 아니라 입력 비트로 보낸다. 조준 방향과 발사 시점의 화면 Tick(`ViewTick`)을 함께 싣는다.
  - 서버가 32 Tick 위치 기록을 되감아 판정한다.
  - Client는 연출만 먼저 보여 준다. 명중·피해는 서버 결과만 표시한다.

### Phase 4 — 인벤토리·Loot
- **행동:** 월드 아이템, 줍기·버리기, 등급, 탄약, 회복을 만들었다.
- **판단:**
  - 줍기는 E 비트 하나다. 서버가 가장 가까운 아이템을 고르고 Client는 아이템 Id를 보내지 않는다.
  - 아이템·Loot 데이터는 서버 JSON에 두고, 시작할 때 검증해 틀리면 서버가 뜨지 않는다.
  - 월드 아이템은 256개가 상한이다.

### Phase 5 — 배틀로얄 규칙
- **행동:** 경기 상태 기계, Safe Zone, 영구 사망, 관전, 순위를 만들었다.
- **판단:**
  - 경기 전에는 피해가 없다.
  - 경기 시작은 한 Tick 안에서 원자적으로 처리한다.
  - 이탈은 탈락으로 처리한다.
  - 판 재시작이 모든 상태를 지워 판이 반복돼도 아무것도 쌓이지 않는다.

### Phase 6 — 맵
- **행동:** 160 m 높이 격자 지형, POI, 건물, Loot·투입 지점을 만들었다.
- **판단:**
  - 언덕 높이는 정수 계산이다. 서버와 Client가 비트 단위로 같은 지형을 얻는다.
  - 모든 경사는 걸어서 오를 수 있게 하고, 테스트로 고정한다.
  - 박스는 평지에만 둔다.
  - 사격 판정도 같은 지형을 쓴다.

### Phase 7 — 봇
- **행동:** 실제 UDP로 접속하는 Headless 봇을 만들고 부하를 쟀다.
- **판단:**
  - 봇은 서버를 참조하지 않는다. Client가 받는 정보만 쓴다. 서버 입장에서는 진짜 Client와 구별되지 않아야 측정이 의미 있기 때문이다.
  - 봇 N명을 스레드 하나(LiteNetLib 수동 모드)로 돌린다.
- **발견:** Snapshot 한 패킷에 50명이 상한이라 64·100명을 잴 수 없었다. 이것이 Phase 8의 입력이 됐다.

### Phase 8 — Snapshot 최적화
- **행동:**
  - Entity를 양자화했다(23 B → 13 B).
  - Snapshot을 패킷당 90명으로 나눠 보낸다.
  - 100명으로 다시 쟀다.
- **판단:**
  - 서버 CPU·할당·Lock 최적화는 하지 않는다. 측정상 병목이 아니었다.
  - Interest Management와 Delta Compression은 미룬다.
  - Client 최적화는 측정 절차부터 만든다.

### Phase 9 — 영속화
- **행동:** MySQL에 경기 기록과 누적 통계를 저장한다.
- **판단:**
  - Game Loop는 경기가 끝나는 Tick에 기록 하나만 큐(16, 넘치면 버림)에 넣는다.
  - 별도 async Writer가 한 경기를 Transaction 하나로 저장한다.
  - ORM 없이 매개변수화한 SQL을 쓴다.
  - 종료할 때는 Game Loop가 먼저 멈추고 Writer가 남은 기록을 저장한다.

### Phase 10 — Hardening
- **행동:** 끊는 이유 코드, 자동 재접속, 재접속 유예, Timeout, 예외 복구, Health 관측을 만들었다.
- **판단:**
  - 경기 중 끊긴 사람의 캐릭터를 10초 지킨다.
  - Input Timeout은 네트워크 Timeout + 2초 이상이어야 한다. 그보다 짧으면 네트워크 끊김이 서버 Kick으로 보여 유예를 잃는다.
  - 예외 복구는 3단계다.
    1. Tick 예외는 그 Tick만 건너뛴다.
    2. 3초 연속 실패하면 경기를 초기화한다.
    3. 10분에 3번 초기화되면 코드 결함으로 보고 서버를 내린다.
  - 인증과 DDoS 방어는 범위 밖이라고 명시했다.

### Phase 11 — 게임 UI
- **행동:** 타이틀·메뉴·끊김·결과·전적 화면, 이름, Kill Feed를 만들었다.
- **판단:**
  - 화면 흐름은 UnityEngine 없는 상태 기계(`UiFlow`)다. 서버 테스트 프로젝트가 그대로 시험한다.
  - UI는 Scene·Prefab 없이 코드로 만든다.
  - 한글은 OS 글꼴을 실행 중에 불러온다.

### Phase 12 — 이동·공중 투입
- **행동:**
  - 이동 모드 7개, 기력·슬라이드·Mantle·Hurdle을 만들었다.
  - 수송기·자유 낙하·글라이더, 낙하 피해, 문을 만들었다.
- **판단:**
  - 이동 상태는 `Mode` 값 하나와 분기 함수다. 클래스 계층을 만들지 않는다.
  - 모든 수치는 Shared 상수 한 곳(`MovementTuning`)에 둔다.
  - 공중 투입은 새 경기 상태가 아니라 `Playing`의 하위 단계다. 새 상태를 넣으면 UI·봇·DB까지 고쳐야 한다.
  - 뛰어내리기·글라이더는 Jump 비트를 다시 쓴다. 새 요청 패킷은 없다.
  - Snapshot Entity는 빈 플래그 비트를 써서 13 B 그대로 지킨다.
  - 서버는 이동 거리 이상을 센다. 부정행위 검출이 아니라 시뮬레이션 버그 검출용이다.

### Phase 13 — 채집·건설
- **행동:** 채집, 격자 건설, 구조물 피해, 지지와 연쇄 붕괴, 건설 복제, 봇 건설을 만들었다.
- **판단:**
  - 건설은 Player Snapshot에 넣지 않고 별도 ReliableOrdered 채널로 보낸다. 큰 Sync가 Snapshot을 막는 Head-of-line Blocking을 피하기 위해서다.
  - 관심 영역(20 m 칸, 64비트 마스크)만 보낸다.
  - 요청은 격자 좌표만 담는다(월드 좌표 float 없음). 서버가 모든 배치 조건을 검증한다.
  - Client 충돌 예측은 서버가 확정한 조각으로만 한다.
- **리뷰에서 고친 것:** 붕괴 판정을 파괴마다 하지 않고 Tick당 탐색 한 번으로 모았다. 10,534개 탑에서 파괴 50개를 처리하는 시간이 64 ms에서 2.45 ms로 줄었다.

### QA 도구 (QA-1–5, 스트레스)
- **행동:**
  - JSON 시나리오로 서버를 띄우고 Headless Actor를 움직여 서버 상태를 검증하는 도구를 만들었다.
  - Web UI, 네트워크 장애 주입(UDP Proxy), Unity Client 자동화·스크린샷, 반복·Seed Sweep·Baseline 비교, 스트레스 시나리오를 더했다.
- **판단:**
  - 서버 QA 코드는 한 폴더에 둔다. `Match`에는 QA 분기를 넣지 않는다.
  - QA 명령은 Game Loop 스레드에서만 실행한다.
  - QA 모드는 Production 환경에서 켜지지 않는다. HTTP는 127.0.0.1에만 연다.
  - Actor는 봇 코드를 그대로 쓴다(도구도 프로토콜만 쓰는 Client다).
  - 반복 실행은 병렬로 돌리지 않는다. 성능 측정을 오염시키지 않기 위해서다.

## 작업 방식

```text
요청서 → 설계(Spec) → 구현 계획(Plan) → 구현 → 리뷰·반박 검증 → 측정 → Push
```

- **설계(Spec):** 결정마다 D번호, 추천 이유, 틀렸을 때의 비용을 적는다([Docs/specs](Docs/specs)).
- **계획(Plan):** Task 단위로 나누고, 바뀐 점은 Spec에 되돌려 적는다([Docs/plans](Docs/plans)).
- **리뷰:** 변경분에 맞는 점검(안전성, Deadlock, Hot Path, DB 등)만 켜서 리뷰한다. 지적마다 반박 근거부터 찾아 확인된 것만 고친다.
- **서버 감사:** 서버 전체를 6개 영역으로 나눠 감사한다(`server-review`).
- **교차 검증:** 다른 모델(Codex)이 읽기 전용으로 검증한다(`codex-review`).
- **측정:** 같은 절차로 Phase마다 다시 재서 이전과 비교한다([LoadTest](Docs/LoadTest.md)).
