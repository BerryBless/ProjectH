# 함수 주석 규칙 (기능 / 입력 / 출력)

코드를 읽지 않고도 함수의 **기능, 입력, 출력**을 빠르게 파악하게 하는 것이 목적이다. 이번 작업에서 추가하거나 수정한 함수에만 적용한다. `game-core-rules`와 같이 모든 코드 작업에 켜져 있다.

## 1. 기본 형식

```csharp
// 기능: 플레이어 ID로 현재 세션을 조회한다.
// 입력: playerId - 조회할 플레이어 ID.
// 출력: 세션이 존재하면 PlayerSession, 없으면 null.
private PlayerSession? FindSession(long playerId)
```

- 각 항목은 한 줄이다. 입력이 여러 개면 한 줄에 쉼표로 잇는다: `// 입력: attackerId - 공격자 ID, targetId - 대상 ID, damage - 적용할 피해량.`
- 입력이 없으면 `// 입력: 없음.`
- 상세 설계는 함수 주석이 아니라 `Docs/`에 쓴다. 함수 주석이 길어지면 읽히지 않는다.

## 2. 출력을 쓰는 법

출력은 반환 타입을 반복하지 않고 **의미**를 적는다. `출력: bool.`은 정보가 없다.

| 경우 | 출력 예 |
|---|---|
| void | `출력: 반환값 없음. 세션과 플레이어 상태가 정리된다.` (무엇이 바뀌는지) |
| bool | `출력: 배치 가능하면 true, 불가능하면 false.` |
| Try 패턴 | `출력: 성공하면 true와 파싱된 입력, 실패하면 false.` |
| async | `출력: 조회된 PlayerStats. 데이터가 없으면 null.` (Task가 아니라 실제 결과) |
| 생성자 | `출력: Waiting 상태로 초기화된 Match 객체.` (초기 상태) |
| 이벤트 Handler | `출력: 반환값 없음. 대상 세션의 연결 상태가 변경된다.` |
| Server Tick | `출력: 반환값 없음. Server Authoritative World State가 갱신된다.` (어떤 상태를 처리하는지 기능에 명확히) |
| Network 송신 | `출력: 반환값 없음. 대상 Client들에게 Snapshot Packet이 전송된다.` |

입력도 타입을 반복하지 않는다. 나쁨: `playerId - long 타입 playerId.` 좋음: `playerId - 조회할 플레이어 ID.`

경우별 전체 예시는 `references/examples.md`를 본다. 처음 쓰거나 형식이 애매할 때만 읽는다.

## 3. 함수 내부 주석

코드만 봐도 알 수 있는 내용(`// 체력을 감소시킨다.`)은 쓰지 않는다. 내부 주석은 다음 이유가 있을 때만 쓴다: 성능상 이유, Thread Safety, Lock Ordering, 특수한 Network 규칙, Lifetime, Workaround, 직관적이지 않은 알고리즘(`game-core-rules` 19절과 같은 기준).

## 4. 적용 범위

순서: 코드 수정 → 이번에 추가·수정한 함수 확인 → 기능/입력/출력 주석 확인 → 누락 추가 → Build/Test.

- **새 함수:** 작성과 동시에 단다. 나중에 몰아서 달면 빠진다.
- **기존 함수 수정:** 이미 있는 주석이 현재 동작과 맞는지 확인하고, 동작이 바뀌었으면 반드시 고친다. "코드는 바뀌었는데 주석은 이전 동작"인 상태는 허용하지 않는다. **잘못된 주석은 없는 주석보다 위험하다** — 읽는 사람이 믿고 틀린 판단을 하기 때문이다.
- **리팩터링:** Parameter 추가 → 입력 수정, Return Type 변경 → 출력 수정, 책임 변경 → 기능 수정, 이름 변경 → 주석 내 참조 수정.
- **기존 주석이 다른 형식일 때:** 수정한 함수의 기존 영어·자유 형식 주석에 담긴 이유(Thread Safety, Lifetime, 설계 결정 번호 등)는 지우지 않는다. 기능/입력/출력 세 줄을 위에 두고, 이유 설명은 그 아래 또는 함수 내부에 남긴다.
- **적용 제외:** 자동 생성 코드, 외부 라이브러리 코드, 단순 lambda, 아주 짧은 local function, 프로퍼티 getter/setter, 단순 record·DTO 필드, enum 값, 테스트 메서드(이름이 곧 설명인 `[Fact]`·`[Test]`). 단, 로직이 들어간 local function과 테스트 헬퍼는 일반 함수처럼 적용한다.
- **일괄 수정 금지:** 주석 형식을 맞추려고 건드리지 않은 함수·파일을 수정하지 않는다. diff가 커져 리뷰가 어려워지고 실제 변경이 묻힌다. 기존 코드 전체 적용은 사용자가 따로 요청했을 때만 하며, 그때도 코드 동작은 바꾸지 않고 주석만 바꾼 별도 Commit으로 나눈다.

## 5. 최종 확인

코드 수정 작업을 끝내기 전에 이번 diff(`git diff`)의 함수마다 확인하고, 작업 보고에 "함수 주석 확인 완료" 또는 남긴 예외를 적는다.

```text
[ ] 새 함수에 기능 주석이 있는가?
[ ] 새 함수의 입력이 설명되어 있는가?
[ ] 새 함수의 출력이 설명되어 있는가?
[ ] 수정한 함수의 기존 주석이 현재 동작과 일치하는가?
[ ] Parameter 변경이 주석에 반영되었는가?
[ ] Return 변경이 주석에 반영되었는가?
[ ] 코드를 그대로 읽어주는 내부 주석을 추가하지 않았는가?
```

## 핵심 규칙

```text
코드를 수정할 때마다 → 수정/추가한 함수의 주석도 확인한다.
주석 형식 → 기능 / 입력 / 출력, 짧고 명확하게.
코드를 그대로 번역하는 주석은 쓰지 않는다.
코드와 주석이 다르면 반드시 주석도 수정한다.
현재 작업에서 건드린 함수에만 자동 적용한다.
```
